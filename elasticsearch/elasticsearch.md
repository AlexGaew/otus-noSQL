# Elasticsearch — Общие сведения

## 1. Что такое Elasticsearch

Elasticsearch — это распределённый поисковый и аналитический движок с открытым исходным кодом, построенный на основе библиотеки Apache Lucene. Он оптимизирован для полнотекстового поиска, фасетной фильтрации и аналитики в реальном времени по большим объёмам неструктурированных и слабоструктурированных данных.

В отличие от классических СУБД, Elasticsearch — это прежде всего поисковый движок: данные в нём индексируются так, чтобы обеспечить максимальную скорость поиска по тексту, фильтрам и агрегациям. Основной формат хранения — документы в JSON, что делает его документоориентированным NoSQL-хранилищем с мощным слоем поиска.

Проект был создан Шей Баноном в 2010 году как надстройка над Lucene с удобным REST API. Сейчас Elasticsearch — часть экосистемы Elastic Stack (ELK: Elasticsearch, Logstash, Kibana) и широко применяется в observability, поиске, аналитике логов и e-commerce.

### Ключевые характеристики

- **Тип**: Distributed full-text search & analytics engine (Document NoSQL)
- **Модель данных**: Документы JSON, организованные в индексы
- **Запросы**: Query DSL (JSON-based), а также SQL-совместимый API
- **Производительность**: Высокая скорость полнотекстового поиска и агрегаций за счёт инвертированного индекса
- **Масштабируемость**: Горизонтальная через шардинг и реплики на уровне индексов
- **Репликация**: Primary/replica shards с автоматическим перераспределением при отказе узла
- **Транзакции**: Не поддерживает транзакции в классическом смысле; операции атомарны на уровне одного документа

### Основные концепции

**Инвертированный индекс**. Ядро поиска в Elasticsearch — это инвертированный индекс, который хранит отображение «термин → список документов». Это позволяет мгновенно находить все документы, содержащие нужное слово или фразу, без полного сканирования.

**Индексы и шарды**. Данные хранятся в *индексах* (аналог таблицы или базы данных). Каждый индекс разбит на *шарды* — горизонтальные фрагменты данных, распределённые по узлам кластера. Каждый шард может иметь одну или несколько *реплик* для отказоустойчивости.

**Документы и маппинг**. Единица хранения — JSON-документ. Структура документа описывается *маппингом* (mapping), который определяет типы полей и способы их индексирования. Маппинг может быть явным (задан вручную) или динамическим (Elasticsearch угадывает типы при первой вставке).

**Анализаторы и токенизация**. Перед индексированием текстовые поля проходят через *анализатор* (analyzer): токенизация, нормализация, стемминг, удаление стоп-слов. Выбор анализатора напрямую влияет на качество поиска.

**Query DSL**. Elasticsearch использует собственный язык запросов на основе JSON — Query DSL. Поддерживаются `match`, `term`, `range`, `bool`, `nested`, `aggregations` и десятки других типов запросов. Также доступен SQL API для простых запросов.

**Кластер и роли узлов**. Кластер Elasticsearch состоит из узлов с разными ролями: `master` (управление кластером), `data` (хранение данных), `ingest` (предобработка документов), `coordinating` (маршрутизация запросов). В небольших кластерах один узел может совмещать несколько ролей.

### CAP-теорема

Elasticsearch по умолчанию ведёт себя как **CP**-система: при записи нового документа с `refresh_interval` и `wait_for_active_shards` гарантируется согласованность на уровне кворума. При сетевом разделении кластер может отказать в записи, но не вернёт устаревшие данные.

На практике поведение гибкое:
- При настройках `wait_for_active_shards=1` запись подтверждается только от primary shard — система становится более доступной, но рискует потерять данные при отказе primary.
- При `wait_for_active_shards=all` система ближе к строгой CP-модели.

Практический вывод: Elasticsearch чаще рассматривают как **CP/гибридную** систему с настраиваемым балансом между консистентностью и доступностью, в зависимости от требований конкретного кейса.

## 2. Для чего использовать Elasticsearch

### Идеальные сценарии

**Полнотекстовый поиск**. Elasticsearch — де-факто стандарт для сложного текстового поиска с учётом релевантности, опечаток, синонимов и морфологии.

Примеры: поиск по сайту, поиск в документах и базах знаний, e-commerce поиск товаров.

**Логи и observability**. В связке с Logstash/Filebeat и Kibana Elasticsearch формирует ELK/Elastic Stack — одно из наиболее распространённых решений для централизованного сбора, хранения и анализа логов.

Примеры: application logs, access logs, infrastructure metrics, distributed tracing.

**Аналитика и агрегации в реальном времени**. Благодаря мощному слою агрегаций (terms, date histogram, percentiles, cardinality и др.) Elasticsearch хорошо справляется с аналитическими задачами по событийным данным.

Примеры: анализ пользовательского поведения, мониторинг KPI, real-time дашборды в Kibana.

**Геопространственный поиск**. Поддержка типов `geo_point` и `geo_shape` позволяет строить запросы по радиусу, bounding box и сложным географическим областям.

Примеры: поиск ближайших объектов, геомаркетинг, логистика.

**Фасетный поиск и фильтрация**. Агрегации Elasticsearch позволяют строить динамические фильтры («фасеты») — категории, диапазоны цен, теги.

Примеры: интернет-магазины, каталоги товаров и услуг, поисковые порталы.

### Когда НЕ стоит использовать Elasticsearch

**Источник истины для критичных бизнес-данных**. Elasticsearch не предназначен как основная транзакционная СУБД: отсутствие ACID-транзакций делает его ненадёжным для финансовых операций и других сценариев, требующих строгой консистентности.

**Частые обновления документов**. Обновление документа в Elasticsearch — это фактически удаление старой версии и вставка новой. При высокой частоте обновлений нагрузка на merge-процессы сегментов Lucene может быть значительной.

**Сложные JOIN между сущностями**. Elasticsearch не поддерживает реляционные JOIN. Для связанных данных приходится использовать денормализацию, `nested` объекты или `parent-child` отношения — всё это имеет ограничения по производительности и гибкости.

**OLTP-нагрузки с транзакциями**. Для приложений с необходимостью транзакций, откатов и сложных консистентных операций лучше подходят PostgreSQL/MySQL.

**Небольшие проекты без поисковых требований**. Если достаточно простого `LIKE`-поиска в SQL-базе, внедрение Elasticsearch избыточно по сложности настройки и эксплуатации.

### Реальные примеры использования

- **Wikipedia**: полнотекстовый поиск по статьям
- **GitHub**: поиск по коду и репозиториям
- **Netflix**: поиск контента и анализ логов
- **Uber**: поиск адресов и геокодинг, анализ операционных логов
- **Airbnb**: поиск жилья по фильтрам и геолокации
- **Elastic (собственный продукт)**: Elastic Security, Elastic Observability

## Краткое резюме

Elasticsearch — это мощный распределённый поисковый и аналитический движок для сценариев с полнотекстовым поиском, логами и событийной аналитикой. Он особенно эффективен в связке с Kibana и Logstash (ELK Stack) для observability и в e-commerce для фасетного поиска. Не подходит как замена реляционным СУБД там, где критичны транзакции, частые обновления данных или сложные JOIN.

## 3. Выполнение домашнего задания

### 3.1 Для выполнения домашнего задания развернем Elastic Search в Docker.
```yml
version: "3.9"

services:
  elasticsearch:
    image: elasticsearch:8.13.4
    platform: linux/amd64
    container_name: es-otus
    restart: unless-stopped
    environment:
      - discovery.type=single-node
      - xpack.security.enabled=false
      - ES_JAVA_OPTS=-Xms512m -Xmx512m
    ports:
      - "9200:9200"
    volumes:
      - es_data:/usr/share/elasticsearch/data

volumes:
  es_data:
```

### 3.2 Состадим индекс с обязательным полем text типа text.
```curl
curl -X PUT "http://localhost:9200/otus_search" \
  -H "Content-Type: application/json" \
  -d '{
    "mappings": {
      "properties": {
        "text": {
          "type": "text"
        }
      }
    }
  }'

  {"acknowledged":true,"shards_acknowledged":true,"index":"otus_search"}
```
## 3.3 создаём index template 
```curl
Method: PUT
URL: http://localhost:9200/_index_template/otus_search_pattern
{
  "index_patterns": ["otus_search*"],
  "template": {
    "mappings": {
      "properties": {
        "text": {
          "type": "text"
        }
      }
    }
  }
}
```
## 3.4. Добавляем три документа с русским текстом.

## 3.5 fuzzy search запрос по фразе "мама ела сосиски".
```
Method: GET
URL: http://localhost:9200/otus_search/_search

{
  "query": {
    "match": {
      "text": {
        "query": "мама ела сосиски",
        "fuzziness": "AUTO"
      }
    }
  }
}
```
